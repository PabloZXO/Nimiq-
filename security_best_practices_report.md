# Повторна перевірка приватності та безпеки NimDuel

Дата: 17 вересня 2026 року. Базова версія: `e8a3a03` та зміни цього аудиту.

## Висновок

Підтверджених критичних або високих вразливостей під час цієї перевірки не виявлено. Автоматичний пошук не знайшов ключів, токенів чи паролів у перевірених файлах та Git-об'єктах. Відбитки справжнього ключа тестового банку і пароля серверної бази також не збіглися з перевіреними матеріалами для публікації. Це результат обмеженого аудиту, а не гарантія відсутності всіх можливих помилок.

Перед зміною видимості GitHub залишається рішення власника щодо особистої електронної адреси у старих комітах. Репозиторій не переводився в публічний режим, історія на GitHub не переписувалася.

## Критичні та високі

Підтверджених знахідок немає. Перехід до реальних коштів цим звітом не дозволяється: застосунок залишається у Testnet.

## Знахідки та зміцнення захисту

### 1. Приватність: особиста пошта в історії — потребує рішення власника

Місце: поля author/committer попередніх 21 коміту Git, а не текст вихідних файлів. Виявлена одна особиста адреса Gmail; її значення навмисно не наведено у звіті.

Наслідок: відкриття репозиторію зробить адресу доступною через історію комітів.

Для наступних комітів локальну адресу автора вже замінено на перевірену GitHub noreply-адресу власника. Це не змінює попередні коміти. Для старої історії потрібне окремо погоджене переписування з резервною копією та перевіркою незмінності вмісту. Воно змінює ідентифікатори комітів і потребує примусового оновлення гілки; саме по собі не гарантує видалення старих об'єктів із кешів GitHub або чужих копій.

### 2. Умовний ризик роздавання приватних файлів — захист додано

Місце: `server/index.mjs:56`, `server/index.mjs:69`.

До зміни статичний сервер міг віддати довільний тип файла всередині `dist`, а перевірка шляху не враховувала переходи через символьні посилання. Для витоку потрібне попереднє потрапляння приватного файла або відповідного посилання в публічну папку. Таких файлів у перевіреній збірці не знайдено; це не свідчення фактичного витоку.

Додано перелік дозволених типів публічних ресурсів, заборону прихованих і службових шляхів та перевірку справжнього шляху файла. Текстові файли доступні лише для ліцензій і повідомлення про прапори. Файли ключів, баз, архівів, карт вихідного коду та посилання за межі публічного каталогу відхиляються.

Перевірка: `tests/security-audit.test.mjs:10` — запити до спеціально створених приватних файлів, закодованих шляхів і посилань повертають 404 без вмісту; звичайні ресурси, ліцензії та маршрути застосунку працюють.

### 3. Низький ризик випадкового додавання службових файлів — захист додано

Місце: `.gitignore:12`.

Раніше вже ігнорувалися `.env`, локальні бази, `data/`, залежності та збірка. Додано окремі правила для ключів, сертифікатів, резервних копій, дампів і архівів. Це додатковий бар'єр проти випадкового коміту; примусове додавання файлів або раніше відстежувані файли він не захищає.

## Обсяг перевірки

- Перевірено 513 історичних blob-об'єктів Git, 1 додатковий локальний blob, 303 відстежувані файли, 213 локальних файлів і 99 записів у локальних архівах на момент початкового сканування. Приватні бази та архіви в `data/` не відстежуються Git і виключені правилами ігнорування.
- Пошук охоплював типові приватні ключі, API-токени, паролі в URL, літеральні секрети, JWT і сесійні значення. Збігів, які сканер класифікував як секрети, не знайдено. Перевірка назв файлів у минулих комітах також не виявила приватних артефактів.
- Окремо на сервері порівняно односторонні відбитки дійсних секретів із кандидатами з Git, поточних відстежуваних файлів та браузерної збірки. Ключ і пароль не копіювалися з сервера. Перевірені типові бінарні, текстові, hex, base64 та URL-кодовані представлення; збігів немає.
- На сервері `.env` і ключ мають права 0600; каталог секретів і каталог даних — 0700. Внутрішні API та PostgreSQL не мають опублікованих портів Docker. Контейнер API працює від непривілейованого користувача з кореневою файловою системою лише для читання.
- Переглянуто авторизацію підписом гаманця, одноразові виклики, ротацію та відкликання сесій, CSRF/origin, доступ до кімнат, профілів, друзів і платежів; серверні відповіді, таймери та результати гри; підтвердження внесків у блокчейні, облік банку, незмінність результатів і повторне надсилання збереженої транзакції виплати після збою.
- Перевірено запуск Stockfish без shell, обмеження черги та вводу, клієнтські сховища й небезпечні операції з HTML. Стек: React/TypeScript і власний HTTP-сервер Node.js. Окремого довідника скіла для цього HTTP-сервера немає; сервер перевірявся за фактичним кодом та інваріантами.
- `tests/security-audit.test.mjs:47` додатково доводить, що сторонній або неавторизований гравець не доходить до фінансового обліку через платіжний endpoint чужої кімнати.

## Результати перевірок

- Повний `npm test`: **146 пройдено, 0 помилок**.
- `npm run build`: успішно. Попередження про розмір JavaScript-пакета понад 500 кБ залишається; це не помилка безпеки.
- `npm audit`: **0 відомих вразливостей**. Тимчасовий збій DNS першої спроби минув, повторний запит успішний.
- `npm run test:browser`: успішно — 6 мов, ширини 320/375/768 px, 24 раунди, усі три рівні вікторин, клавіатура, рахунок, пропуск, оновлення, перегляд відповідей, задачі, діалоги, сценарії гаманця та платежу з підставним провайдером, підбір суперника і відновлення після втрати мережі.
- Усередині серверного контейнера: **15 тестів** доступу, авторизації й HTTP-захисту пройдено. Окрема інтеграційна перевірка PostgreSQL внесків, повернень, збереження зобов'язань, незмінності розрахунку та виплат після збою — **1 пройдена**, в ізольованій тестовій базі.
- Серверний захист розгорнуто після перевірки початкових хешів і відсутності активних кімнат. Старі файли та знімок SQLite збережено у приватній резервній копії. Конфігурація, секрети й проксі не змінювалися.
- Після оновлення API та PostgreSQL: running/healthy, RestartCount 0; HTTPS, JavaScript, CSS і ліцензії доступні. Запити до `.env`, ключа, бази та `.git/config` повертають 404. Платіжний сервіс ready у `testalbatross`.
- Під час початкової синхронізації вузла були повідомлення BLS-кешу й тимчасової відсутності придатного peer. Після синхронізації платежі ready; в окремому повторному вікні свіжих логів за хвилину помилок немає.

## Межі

Це не незалежний пентест або доказ неможливості шахрайства. Не виконувалися повне навантажувальне тестування, перевірка всіх версій WebView, аудит хост-машини й інших її проєктів, аналіз невідомих способів маскування секретів або перевірка чужих копій репозиторію. Безпека зовнішніх залежностей обмежена доступними повідомленнями про вразливості та переглянутими інтеграціями.

Попередня перевірка Mini App у `docs/RELEASE-CHECK.md` має 21 PASS, 1 FAIL, 10 SKIP. Повний поточний платіжний сценарій на фізичних телефонах у Nimiq Pay залишається неперевіреним; браузерний підставний провайдер цього не замінює. Цей аудит не змінює статус цього пункту та не є поданням роботи на конкурс.
